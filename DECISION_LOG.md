# Aegis Fraud Triage — Decision Log

This is the living architecture-decision record (ADR) for the MVP. It records what was chosen, why, trade-offs, and the implementation state so the final interview documentation can distinguish current behaviour from planned work.

| ID | Decision | Why | Trade-off / control | Status |
|---|---|---|---|---|
| D-001 | Build an Australian banking scam and fraud triage copilot, not an autonomous banking agent. | It is a realistic, high-stakes use case that demonstrates routing, RAG, tools, safety, evidence and evaluation. | The agent gives guidance and triage only; it does not move money, block accounts or contact customers. | Implemented |
| D-002 | Use **Aegis Fraud Triage** as the working project name. | Distinct from the earlier Meridian Scam Copilot name and appropriate for a protective, enterprise-facing system. | Brand can change later without affecting the architecture. | Implemented |
| D-003 | Keep the agent graph deliberately small: input guardrail → route → retrieval → gated optional tool use → draft → generation/evidence/output gates → release decision. | A compact graph is explainable in an interview and makes every safety decision observable. | Less autonomous flexibility than a fully open-ended agent; appropriate for banking risk. | Implemented |
| D-004 | Require retrieval quality before considering tools. | A policy-grounded answer is preferable to unnecessary account-data access. | Some user questions will abstain or escalate rather than attempt a tool call. | Implemented |
| D-005 | Enforce tool authorisation using identity, ownership, consent, scope and payload constraints. | Least-privilege access is essential in a banking setting. | Mock tools are intentionally restrictive and may deny some otherwise useful requests. | Implemented |
| D-006 | Use deterministic input, retrieval, generation, evidence and output gates, with a separate response-release policy. | Deterministic checks are auditable and cheap; release policy turns the checks into a safe action. | They cannot judge every subtle semantic claim; LLM judging and human calibration complement them. | Implemented |
| D-007 | Use HITL for any tool use, urgent/card/payment/credential case, gate failure, abstention, high/critical risk, or confidence below 0.85. | Beta users need a defensible safety boundary before trusting automated guidance. | Automated release is intentionally rare; beta throughput is lower. | Implemented |
| D-008 | Start beta with review-all behaviour for externally consequential recommendations. | Builds stakeholder confidence and creates labelled feedback for calibration. | Human-review operations are required; a later risk-based release policy can be tested only after evidence supports it. | Implemented |
| D-009 | Maintain a 100-case golden dataset with expected routes, citations/chunk IDs, tools, gate outcomes and release/handoff outcomes. | Evaluating the whole trajectory prevents a superficially good final answer from hiding unsafe intermediate behaviour. | Synthetic/source-derived data needs periodic expert review and refresh. | Implemented |
| D-010 | Evaluate offline with code-based trajectory and RAG checks, RAGAS when provider access is wired, LLM-as-judge, and human calibration. | Each method covers different failure modes: deterministic contracts, RAG quality, nuanced groundedness, and domain validity. | LLM judges can drift or share bias with the agent; maintain a human-labelled calibration set. | Partly implemented |
| D-011 | Record one local JSONL trace per run, add OpenTelemetry spans, and send nested traces/evaluations to LangSmith. | The demo needs both an operational dashboard and drill-down trajectory evidence. | Dual telemetry adds configuration and data-governance work; traces must remain redacted. | Local/OTel implemented; LangSmith configuration verified |
| D-012 | Use Pinecone for vector storage and hosted embeddings. | The ready serverless index is operational, and hosted embedding avoids another credential/provider for the MVP. | The selected index has a fixed 1024-vector dimension, so embedding-model changes require compatibility validation or a new index. | Implemented; graph-constrained live retrieval smoke-tested |
| D-013 | Use Nebius as the initial model provider: Qwen3-30B for the agent and a larger different-family model for LLM judging. | It gives adequate quality and a sensible latency/cost profile, while a separate judge reduces same-model bias. | The judge still needs calibration against human labels; a second provider can be added later for stronger independence. | Implemented; live drafting and judge validation active |
| D-014 | Use LangSmith APAC for traces and experiments. | The account authenticated only against the APAC endpoint. | LangSmith is an external telemetry processor; no raw PII or credentials should be included in trace metadata. | Configuration and connectivity verified |
| D-015 | Keep Mem0, LlamaIndex cloud services and banking credentials out of the MVP. | Long-lived memory is not necessary for a sensitive, case-based scam triage flow; the agent does not need real banking access to demonstrate secure tool boundaries. | Personalisation and real operational integration are deferred to a governed production phase. | Implemented |
| D-016 | Use a Grafana-based Operations Command Centre for the monitoring demo, with Prometheus metrics, Loki logs and Tempo traces; retain Streamlit for agent interaction and HITL review. | Grafana communicates a credible production monitoring posture and supports high-signal executive views plus operational drill-down. | It adds Docker/Desktop setup; a read-only local metrics exporter keeps the agent implementation and data boundary simple. | Scaffolded; Docker Desktop required to run |
| D-017 | Upgrade the collector design to Grafana Alloy (an OpenTelemetry Collector distribution) and remove Promtail. | Promtail reached end of life in March 2026; Alloy is maintained and can collect both OTLP traces and redacted file logs. It adds batching and memory limits before traces reach Tempo. | The local Compose stack becomes more operationally realistic but still needs managed infrastructure, TLS and access controls for deployment beyond a controlled environment. | Implemented and awaiting Docker validation |
| D-018 | Activate Pinecone as the live graph-constrained retrieval backend in the local runtime. | A 1024-dimensional Pinecone embedding check, isolated `policy-v1` namespace ingestion and end-to-end PayID retrieval test all succeeded. | The retriever fails closed: missing credentials, provider errors or missing required graph nodes produce insufficient evidence, preventing tool use and forcing abstention/HITL. | Implemented and smoke-tested |
| D-019 | Use Nebius only for evidence-constrained response drafting after retrieval and tool controls. | A live synthetic PayID case produced a structured draft that passed the citation, generation, evidence and output-safety gates, while still requiring human review. | The LLM may fail or produce an invalid draft; the system falls back to deterministic guidance and the downstream gates remain authoritative. | Implemented and smoke-tested |
| D-020 | Load `.env` automatically in local Streamlit and CLI entry points, without changing library defaults. | It makes the configured live stack work reliably from VS Code while unit tests and baseline evaluation remain deterministic unless a live mode is explicitly selected. | Hosted deployments should inject environment variables through a secret manager; `.env` remains local-only and excluded from source control. | Implemented |
| D-021 | Compare baseline, local graph, Pinecone retrieval and live Pinecone-plus-Nebius configurations using the same frozen dataset. | This isolates the value and operational cost of retrieval and generation changes instead of presenting one unverifiable final score. | Live runs are slower and consume provider credits; all reports retain route, trajectory, evidence and gate metrics for diagnosis. | Implemented; live calibration run in progress |
| D-022 | Use an independent Nebius judge for offline faithfulness, safety, escalation and actionability scoring, calibrated against human labels. | An independent judge adds semantic signal beyond exact contracts and avoids judging an agent solely with its own model family. | It is not a release gate until at least 15 human labels achieve >=0.80 mean exact agreement. | Implemented; human review pending |
| D-023 | Pin RAGAS to 0.3.9 and LangChain Community below 0.4. | RAGAS 0.4.3 currently fails to import with modern LangChain Community due to a removed VertexAI import path. The pin was verified locally. | Pinning trades newest features for a reproducible evaluation environment; review the upstream issue before upgrading. | Implemented |
| D-024 | Publish the immutable, synthetic golden set to LangSmith once and do not duplicate it on repeated runs. | It makes the same cases available for LangSmith experiment comparison while avoiding customer-data exposure and duplicate examples. | The current runner produces local report artefacts; a later integration can post aggregate scores to named LangSmith experiment runs. | Implemented; dataset `aegis-fraud-triage-golden-v1.3` published |
| D-025 | Measure citation accuracy as provenance against the evidence retrieved in the same run, and measure required-citation coverage separately. | Valid additional citations from retrieved public-safety material should not be misclassified as hallucinations merely because they are not in the minimum gold list. | A response may still be incomplete; required-citation recall remains a separate release diagnostic. | Implemented |
| D-026 | Report unsupported RAGAS metrics as unavailable rather than coercing provider incompatibilities to a numeric score. | A single-generation provider cannot faithfully calculate Answer Relevancy, which requests multiple generations. | The missing signal is visible and must be resolved or replaced before using it as a release metric. | Implemented |
| D-027 | Prioritise active remote-access or credential compromise over routine payment routing, and distinguish an outcome promise from a statement that no outcome can be guaranteed. | A stratified live run exposed a missed critical escalation and a false-positive output-safety gate. | The corrected PayID/remote-access regression passes routing, escalation, evidence/citation, tool contract, review routing and all gates. The full 100-case run is retained and still has residual misses, so no release threshold changes. | Implemented and targeted-live-regression tested |
| D-028 | Where human reviewers are unavailable, use an automated judge-validation pack instead of claiming human calibration. | The project still needs a repeatable semantic validation signal for the interview demo. Strict evidence and safety-red-team rubrics plus deterministic contracts expose more failure modes than one generic judge. | Both profiles may use the same provider/model, so correlated blind spots remain. The pack always retains mandatory review for consequential cases and is explicitly not human calibration. | Implemented; pre-fix full pack retained and post-fix sample active |
| D-029 | Make output-safety checks semantically specific enough to distinguish safe prohibitions from sensitive-data requests, and accept equivalent urgent-human-review language. | The full live run surfaced 15 false-positive output-safety failures from correct safety wording, obscuring the meaningful controls. | Regression tests cover the observed phrases. Preserve the pre-fix run as evidence; the targeted correction passed and the full rerun improved guardrail compliance to 0.980, while residual failed cases remain for analysis. | Implemented; post-fix full evaluation retained |
| D-030 | Export application spans through Alloy to Tempo using an explicit OTLP HTTP exporter dependency and Docker-network Tempo receiver bindings. | The first end-to-end telemetry check showed JSONL/metrics working but exposed a missing exporter package and a Tempo receiver bound to container localhost. | Alloy receiver and exporter counters confirmed a synthetic application span reached the collector and was forwarded to Tempo. Production still requires mTLS and private networking. | Implemented and verified locally |
| D-031 | Insert mandatory urgent-human-review language before response gates, rather than appending it after output-safety evaluation. | Targeted regression showed the final response was safe, but the gate had evaluated an earlier draft and emitted a false failure. | The final draft now has its release-required handoff before citation/evidence/output checks. The four-case targeted output-order suite passed; full-suite residual misses remain visible and mandatory review for consequential cases continues. | Implemented and targeted-regression verified |
| D-032 | Use deterministic scenario-stratified sampling for semantic RAGAS and automated-judge packs. | A fixed 50/30/15/5 mixture makes a smaller provider-costed run represent both routine and adversarial risk better than taking the first N rows. | A 30-case pack is a diagnostic sample, not a replacement for full evaluation or independent human calibration. | Implemented |
| D-033 | Increase autonomy through high-recall safety routing, validated response envelopes and reversible review packages—not through broader banking permissions. | The main readiness gap was missed critical escalation, while reviewers still needed complete context to act efficiently. | The full live frozen run reached 1.000 critical-escalation recall, but escalation precision fell to 0.731 and one refund-fee report was misrouted. Keep the conservative threshold and fix retained routing regressions before considering a release-policy change. | Implemented and live-evaluated |

## Provider configuration decisions

- Pinecone index: `aegis-fraud-triage-dev`; cosine similarity; 1024 dimensions; readiness verified.
- Nebius base URL: `https://api.studio.nebius.ai/v1`; credentials and model-list access verified.
- LangSmith endpoint: `https://apac.api.smith.langchain.com`; credentials verified. Project: `aegis-fraud-triage`.
- Secrets reside only in `.env`, which must stay out of source control and trace payloads.

## How to update this log

For a material decision, add a new ID rather than silently editing history. Mark a decision `Superseded` if a later one replaces it, and link the related architecture, gate-policy, evaluation, or monitoring document.
